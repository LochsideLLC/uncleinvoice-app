# Stripe Connect and invoice tracking: test-mode plan

Status: implemented on `feat/stripe-connect-foundation`, not migrated or deployed. Live payments, automatic notification email, push dispatch, and view tracking default to off.

## Architecture

- Keep the existing session auth, Prisma database, invoice PDF renderer, Resend sender, and Bookkeeper workflow. No second auth system.
- An invoice belongs to its issuing contractor. A registered contractor can create a hashed, revocable 256-bit hosted link. Bookkeeper-prepared invoices default to `collectionMode=documentation` and `onlinePaymentEnabled=false`. Guests keep the existing PDF and print flow but have no Connect or hosted-link controls.
- Accounts v2 are created with `dashboard=full`, `fees_collector=stripe`, and `losses_collector=stripe`. `requirements_collector=stripe` is read back and required before payments. Stripe-hosted onboarding collects business and bank information. Old Express accounts are never reused. The platform stores only the Stripe account ID and capability state.
- The first release supports US businesses and USD invoices. Stripe requires `identity.country=us` when creating an account with `defaults.currency=usd`.
- Checkout is created on the connected account with `stripeAccount`, no transfer and no application fee. The server calculates the invoice balance. One active Checkout attempt per invoice is stored with an idempotency key. Existing open sessions are reused only while amount, currency, and account still match. Changed open sessions are expired. Browser redirects never mark an invoice paid.
- The pay button remains blocked until Stripe reports card payments active, charges and payouts enabled, and account details submitted. Fee, loss, dashboard, and requirements responsibility are checked again at each sync.
- A separate signed Connect webhook retrieves current Stripe state on the connected account, checks invoice/account/amount/currency, and records each event ID once. A row lock serializes payment balance updates. Payment and delivery are separate state dimensions. Payment rows and the event timeline preserve Stripe IDs, refunds, disputes, and manual entries.
- The hosted page uses the existing invoice layout, noindex and no-store headers. A same-origin browser POST records an approximate opened-link count after bot and daily-cookie filtering. Owner and bookkeeper previews are excluded. This does not prove who read the page or track PDF opens.
- In-app notifications are stored per user. Push subscriptions are AES-GCM encrypted and limited to five devices per user. Push and notification email have separate opt-in preferences, dedupe records, daily quotas, and off-by-default switches. SMS and background reminder jobs are absent.
- Daily caps apply to invoice creation, view events, Checkout sessions, PDF rendering, email recipients, push sends, and attachment uploads. Existing attachment storage now has fixed byte limits. These caps limit application writes; they cannot cap inbound Netlify requests before Netlify bills them.

## Live gate and financial exposure

**Do not turn on live payments yet.** Stripe's public [Connect pricing](https://stripe.com/connect/pricing) says the Stripe-prices-users arrangement has no added platform account/payout fee; its [Accounts v2 configuration guide](https://docs.stripe.com/connect/accounts-v2/connected-account-configuration) says full dashboard requires Stripe fee and loss responsibility. Confirm the actual platform's contract, countries, controller values, refund/dispute duties, negative-balance exposure, and eligibility for that arrangement with Stripe before any live key or live webhook is allowed. A self-reported account type is insufficient. Direct charges leave connected contractors responsible for payment fees, refunds, and chargebacks, but Uncle Invoice still has contractual, security, support, and hosting duties. No absolute zero-risk claim is made.

Netlify has a 3,000-credit Pro plan with auto top-up off (checked in Phase 0). Supabase spend-cap state and storage overage terms remain unverified; keep deployment blocked until a real hard cap is confirmed. Cloudflare DNS is in use; no new paid product was added. Resend [lists a free 3,000/month and 100/day allowance](https://resend.com/pricing), but the actual team plan and overage toggle were not verified. Web push has no new paid provider, but server requests and database rows still consume hosting resources. PDF generation and webhook delivery also consume Netlify/Supabase usage. Provider alerts are not hard caps.

The migration enables RLS with default-deny access on every table in the `uncleinvoice` schema. The existing Prisma connection uses a privileged Postgres role that bypasses RLS, so every server action and route must still check the session and invoice owner. No production migration or destructive database operation has been run.

## Known limits

- Checkout, connected webhooks, and Prisma queries have not been tested end to end against isolated full Postgres plus an onboarded Stripe test account. The PGlite migration, pure state, and signature tests do not replace that run.
- A read-only check of an existing test account returned `dashboard=express`, `fees_collector=application_express`, and `losses_collector=application`: unsafe for this design. The first test creation failed before account creation because `identity.country` was missing; corrected creation and onboarding-link generation passed.
- A Checkout session already open in another browser can race with a manual payment. Manual payment is blocked while online collection is enabled; old Checkout sessions are expired when a changed balance is detected at the next Checkout request. A payment completed during an unavoidable cross-system race is recorded even if it overpays; it is never silently discarded.
- The `account.updated` webhook and manual “Check status” refresh capability state. Accounts v2 thin events may need a separate event destination in a future version; test this on the actual Stripe account.
- Disconnection is local and allowed only before any Checkout attempt exists. Accounts with payment history need support and Stripe account management for obligations. It does not delete the Stripe account.
- Bank payout status is not shown; a succeeded customer payment is not a confirmed bank payout.
- Overdue reminders are opt-in in settings but no scheduler runs them. Email notifications remain disabled pending provider verification. In-app history shows the latest 100 events and notification history is pruned after 90 days when new events arrive.
- No desktop/mobile browser layout run was done in this isolated worktree. Static build, lint, and tests are recorded in `HANDOFF.md`.
- `npm audit --omit=dev` still reports 3 high findings in the Prisma 6 toolchain, requiring a separate major upgrade. The critical Next.js findings were removed by updating to 16.3.8.
